# 화면해독 (screen-decode)

기획자의 화면설계서 PDF를 디자이너의 작업 언어로 옮기는 스킬이다.
설계서는 보통 "왼쪽 와이어프레임 + 오른쪽 번호 붙은 디스크립션" 형태이고, 기획 관점(정책·데이터·개발 메모)이 섞여 있다. 디자이너에게 필요한 것은 **어떤 화면이 있고, 화면마다 무엇을 그려야 하며, 어떤 상태까지 만들어야 하고, 아직 정해지지 않은 게 무엇인지**다. 이 스킬은 그것만 골라 정리한다.

## 작업 순서

### 1. PDF 전체를 읽고 화면 목록 뽑기
- Read 도구로 PDF를 읽는다. 10페이지가 넘으면 `pages`로 20페이지씩 나눠 끝까지 읽는다. 표지·변경이력·목차도 훑어서 프로젝트명, 버전, 작성일을 챙긴다.
- **개정 이력에서 이번 버전의 변경점을 뽑는다.** 디자이너가 이전 버전으로 이미 작업 중이라면 가장 먼저 알아야 할 정보다. 결과 파일 맨 위에 적고, 해당 요소에는 `(v1.1 신규)`처럼 버전을 붙인다(수정이면 `(v1.1 수정)`).
- 와이어프레임이 이미지로만 되어 있는 페이지는 텍스트 추출에 기대지 말고 페이지 이미지를 직접 보고 읽는다.
- 화면마다 **화면 ID**(설계서에 있으면 그대로, 없으면 `S-01`처럼 순서대로 부여), **화면명**, **원본 페이지 번호**를 목록으로 만든다. 한 화면이 여러 페이지에 걸치면 `p.5–7`처럼 범위로 적는다.

### 2. 화면별로 디자인에 필요한 내용 정리
화면마다 아래를 뽑는다.
- **목적**: 이 화면에서 사용자가 하는 일 한두 줄
- **UI 요소**: 디스크립션 번호 순서대로 요소명, 종류(버튼·입력창·리스트·탭·토글·모달·바텀시트·토스트 등), 설명
- **상태**: 기본 / 빈 상태 / 에러 / 로딩 — 설계서에 정의된 내용만 적는다
- **인터랙션**: 탭·스와이프·스크롤 시 동작, 이동하는 화면(화면 ID로 연결)
- **문구**: 버튼·타이틀·안내·에러 메시지 원문

정리할 때 지킬 표기:
- **예시 데이터 구분**: 와이어프레임 속 상품명·가격·날짜·이름·건수 같은 값은 실제 확정 값이 아니라 예시다. 문구에 섞어 쓰면 디자이너가 고정 문구로 착각하므로 `예시 데이터:` 줄에 따로 모은다. 변하는 부분이 있는 문구는 `"재고 N개" (예시: "재고 3개")`처럼 규칙과 예시를 함께 쓴다.
- **출처 표시**: 와이어프레임에는 있는데 디스크립션 표에는 없는 요소·문구(헤더, 플레이스홀더, 화면 타이틀 등)는 `(와이어프레임 기준)`을 붙이고, 번호가 없으면 `#` 칸에 `–`을 쓴다. 기획 의도로 확정된 건지 그림으로만 그려진 건지 디자이너가 구분할 수 있어야 한다.
- **줄바꿈 표기**: 팝업·타이틀 문구의 원문 줄바꿈은 `⏎`로 표기한다. 문구 안의 `/`나 `·`는 원문 그대로 두고 줄바꿈 표기로 쓰지 않는다. 파일 맨 위 표기 안내에 이 규칙을 적는다.

기획·개발 전용 내용(API, DB 필드, 로그 정책 등)은 디자인에 영향을 줄 때만 한 줄로 남긴다. 예: "최대 20자 제한 → 입력창에 글자 수 카운터 필요할 수 있음(확인 필요)".

### 3. 빠진 것·애매한 것을 '기획자에게 물어볼 것'으로 모으기
정의되지 않은 상태, 페이지끼리 어긋나는 내용, 문구 오탈자 의심, 이동할 화면이 없는 버튼 등을 모은다. 질문마다 관련 화면 ID와 페이지 번호를 달고, 기획자가 바로 답할 수 있게 "~인가요?" 형태로 쓴다.

질문은 두 그룹으로 나눈다. 질문 30개가 한 표에 섞여 있으면 기획자가 무엇부터 답해야 할지 모르고, 디자이너도 어디서 막히는지 안 보이기 때문이다.

- **디자인 전에 꼭 확인 (최대 7개)**: 답이 없으면 화면을 그릴 수 없거나, 그려도 다시 그려야 하는 것. 예: 비어 있는 에러 규칙·문구, 설계서에 없는 다음 화면, 화면 모양이 바뀌는 상태(마감·품절 등), 빠진 탭이나 영역의 구성.
  - **목록 화면의 빈 상태**와 **로딩·스피너 노출 기준(몇 초부터 띄우는지)**은 정의되지 않았으면 항상 여기에 올린다. 목록 화면은 빈 상태가 가장 자주 보이고, 스피너 기준이 없으면 모든 로딩 화면의 디자인이 정해지지 않는다.
  - 후보가 7개를 넘으면 디자인을 더 많이 막는 순서로 7개를 고르고, 나머지는 '나중에 확인'으로 내린다.
- **나중에 확인**: 디자인을 진행하면서 답을 받아도 되는 세부 사항(아이콘 위치, 띄어쓰기, 버튼 비활성 표시 등).
  - **상태 4종이 빠진 건 상태마다 질문을 따로 만들지 않고, 화면별로 한 줄로 묶는다.** 예: '빈 상태는?', '에러는?', '로딩은?' 세 줄이 아니라 `S-02 · 상태: 빈 상태(이미지 없음)·에러·로딩은 어떻게 보여주나요?` 한 줄. 이미 '꼭 확인'에 올린 상태는 이 줄에서 뺀다.

### 4. 화면해독.md로 저장
- 프로젝트의 `output/` 폴더에 `<PDF 파일명>_화면해독.md`로 저장한다. 폴더가 없으면 만든다. 같은 이름 파일이 이미 있으면 덮어쓰지 말고 사용자에게 먼저 묻는다.
- 아래 "결과 파일 형태"를 따른다.

## 꼭 지킬 것

1. **없는 내용은 지어내지 않는다.** 설계서에 없는 요소·문구·상태를 그럴듯하게 채우면 디자이너가 그걸 확정된 내용으로 믿고 작업하게 된다. 정의되지 않은 칸은 `미정의`로 쓰고 '기획자에게 물어볼 것'에 올린다.
2. **문구는 원문 그대로 옮긴다.** 띄어쓰기·문장부호까지 바꾸지 않는다. 문구는 기획·마케팅이 승인하는 영역이라 디자이너가 임의로 고치면 안 되기 때문이다. 오탈자가 의심되면 원문 옆에 `(오탈자 의심)`만 붙이고 질문 목록에 올린다.
3. **원본 페이지 번호를 단다.** 모든 화면 섹션과 질문에 `p.번호`를 붙여서 디자이너가 원본을 바로 펼쳐볼 수 있게 한다.
4. **디자이너 눈높이 용어로 쓴다.** 컴포넌트, 상태, 바텀시트, 토스트, 모달처럼 디자이너가 쓰는 말로 정리한다. 다만 정리하는 스킬이지 디자인하는 스킬이 아니므로 레이아웃·색·스타일 제안은 하지 않는다.


## 끝내기 전 확인

저장하기 전에 아래를 스스로 점검하고, 어긋난 게 있으면 고친 뒤 저장한다.

- [ ] **화면 빠짐 없음**: 1단계에서 뽑은 화면 목록과 본문 섹션 수가 같고, PDF의 화면 페이지가 모두 어딘가에 들어갔다.
- [ ] **상태 4종 체크**: 모든 화면에 기본·빈·에러·로딩이 적혀 있다. `미정의`인 상태는 질문 목록에 올라가 있다(화면별 한 줄, 또는 '꼭 확인'). 해당 화면에 의미가 없는 상태는 `해당 없음`으로 적는다.
- [ ] **페이지 번호 누락 없음**: 모든 화면 섹션 제목과 질문에 `p.번호`가 있다.
- [ ] **질문 나눔**: '꼭 확인'이 7개 이하이고, 목록 화면 빈 상태·스피너 노출 기준이 미정의라면 '꼭 확인'에 있다. 화면 목록 표의 질문 수와 질문 표의 행 수가 맞다.

저장 후 사용자에게 3줄로 보고한다.

```
저장: output/<PDF 파일명>_화면해독.md
화면: N개
기획자 확인 필요: M건 (꼭 확인 A건 · 나중에 확인 B건)
```
